## 0. Fix first: overnight triage writes rejected every night since 2026-09-19

- **What:** migration 0052 added `tasks.ai_state = 'declined'`, and `app/lib/mcp/validate.ts:325` accepts it. But the zod input schema for MCP `update_task` (`app/api/mcp/[transport]/route.ts`, ~566 on main / 582–583 on task-energy) is still `["planned","building","built","failed"]`. The same gap exists in the `list_code_tasks` filter (route.ts ~217–218) and its type in `app/lib/mcp/reads.ts`.
- **Effect:** `overnight/run.mjs:705-709` sends the triage notes **and** `aiState:"declined"` in one call. The schema check rejects the whole call, so the decline reason is lost too. `ai_state` stays null, and the same tasks are re-triaged every night. 13 rejected writes on 2026-10-19 alone (`overnight/logs/2026-10-19.log`).
- **Why tests missed it:** they exercise the validator, not the registered zod schema.
- **Fix: PR #28** (`ai/fix-ai-state-declined`, https://github.com/Luccama700/mindboard/pull/28). A single `AI_STATES` source of truth feeds every schema and filter, and a regression test runs through the real registered zod schemas (5 of 9 fail on the old code). Gates: lint 0 errors, 1,428 tests pass, build ok. Not merged; Lucca merges, then merges main into `task-energy`.

## 2. `task-energy` adversarial review

Vitest: 82 files, 1,511 tests, all pass. No data-loss or tenant-isolation bugs found. **Merge blockers: #1, #2 and #3. #4 should go in the same pass.**

1. **Pulling a parent's due date earlier silently rewrites its subtasks.** (Medium, high confidence.) `app/actions/tasks.ts:249-260`, `app/lib/mcp/writes.ts:1919-1932`.
   - The confirm summary says "due → X" for one task, but N+1 rows change.
   - Only the parent's Google Calendar event is re-synced (`tasks.ts:372`, `writes.ts:1984`), so a pushed subtask's event goes stale.
   - The subtask writes happen *before* the parent update, so a failed parent update leaves the subtasks already moved.
   - Fix: list the pulled-in steps in the summary, re-sync their events, and update the parent first.
2. **`delete_task` hides the cascade.** (Medium, high.)
   - `writes.ts:2051` says "this cannot be undone" but doesn't mention that the FK cascade deletes every subtask, completed ones included.
   - The web label counts only subtasks in the current view, so a cross-group parent shows a plain "delete".
   - Fix: count the subtasks into the summary.
3. **A subtask's due date can be cleared, which orphans it.** (Medium-low, high.)
   - `tasks.ts:233` / `writes.ts:1899` only guard against tasks that *have* children.
   - Clearing a child's date drops it from the planner and NOW/LATER, while the parent still counts it as open ("2 of 3" forever).
   - MCP `create_task` already requires a subtask due date (`writes.ts:~817`).
   - Fix: reject `dueDate:null` when `parent_task_id` is set.
4. **MCP `complete_task` no longer completes a missed or done task, and the error is misleading.** (Medium-low, high.)
   - `lifecycle.ts:92-99` only updates open tasks and otherwise reports "resolved meanwhile", which reads like a race.
   - Fix: load the status first, then allow missed→done deliberately, or return "already done/missed".
5. **Counts still include hidden subtasks.** (Low-medium.)
   - `app/lib/snapshots/tasks.ts:22-29` feeds MCP `tasks_snapshot` (`reads.ts:162`) and the assistant `get_snapshot` (`tools.ts:901`). Subtasks of a missed parent inflate "overdue", and windows are counted by end date rather than planned day.
   - `stream.ts:874` counts every subtask in the inbox nudge.
6. **The planner pulls steps early at the edge of calendar coverage.** (Low-medium.)
   - Days without calendar data are treated as unusable, so a window straddling the month-grid edge lands on the last covered day and then jumps when the month rolls over.
   - The energy budget plans over 3 days, `get_snapshot` over 7.
   - The existing test (`__tests__/subtask-plan.test.ts:102`) doesn't cover a straddling window.
7. **Snooze/defer can silently do nothing.** (Low-medium.)
   - Web: `stream-client.tsx:832` sets `notBefore = min(dateKey, due_date)`, which is a no-op at window end. The card disappears and then comes back.
   - Watch: `writes.ts:296` returns ok with a new `atWindowEnd` flag that old builds ignore.
   - The watch sorts subtasks by window end, not planned day (`watch/today.ts:216-218`).
8. **Breakdown edge cases.**
   - An overdue parent pays for the Haiku call before validation rejects it (`decompose.ts:185` vs `decompose-ops.ts:69`).
   - Count errors are ignored (`decompose.ts:95-102`).
   - Two simultaneous confirms create two sets of steps.
   - `recordProposal` can throw, and nothing catches it in `proposeBreakdown`.
9. **`create_task` with `parentTaskId` previews the wrong group.** The executor inherits the parent's group (`writes.ts:823`), but the preview names the requested one.
10. **Migration 0053 (flagged; do not auto-apply).**
    - The composite same-user FK is good, RLS from 0001 covers the new columns, and no backfill is needed.
    - Gaps: nothing in the DB blocks self-parenting or nesting deeper than one level. Suggest `check (parent_task_id is distinct from id)`. Also, the cascade wipes completed subtasks' history.
    - **Deploy order:** every task read now selects the new columns, so the migration must be applied *before* this code ships.
11. **Minor.**
    - Completing a parent adds N+1 to "done this week".
    - MCP `create_task` marks energy as the AI's guess, but `update_task` marks it as the user's, so agents can write "user-owned" energy values.

**Missing tests:** subtask pull-in combined with calendar sync and its summary; a window straddling coverage; clearing a subtask's date; `tasksSnapshot` with a missed parent; two breakdowns confirmed at once; the watch's `atWindowEnd`; and the MCP input schema itself (the `declined` gap).

## 3. Architecture audit (main @ b2479d7)

Main's suite: 76 files, 1,419 tests green, run once in a scratch copy. No edits, no production calls. **Clean areas, don't spend time here:** RLS is on for all 41 tables, every FK has ON DELETE, migration numbering is clean, the dispatch claim logic is guarded and tested, and MCP error shapes are consistent.

Ranked:

1. **`declined` enum.** Covered in §0, confirmed at `route.ts:565-566` and `:215-216` on main. Add to the fix: in `run.mjs`, treat "Input validation error" as FATAL for the phase, so it can't fail quietly every night again.
2. **Reads swallow PostgREST errors and report "all clear".** (M, high payoff.)
   - `const { data } = await …` with the error ignored appears 17× in `app/lib/mcp/reads.ts` and 24× in `writes.ts`. A failed query returns `[]`, so agents, digests and overnight read "nothing to do".
   - Typical trigger: selecting a column before its migration is applied. `task-energy` hits exactly this risk with 0053.
   - Fix: a `must(res, what)` helper that throws on `error`, applied mechanically; `guard()` already maps throws to tool errors.
   - Follow-on: a schema-health endpoint (select newest columns `limit 0`) that the morning digest checks.
3. **`tasks_snapshot` 13-vs-1: resolved, not a bug.** Re-read at 02:40: `overdue 1, done 8, missed 4`, versus `13 / 0 / 0` around 01:30. The 12 tasks were resolved by hand (UI/watch) between the reads. The code checks still found two real issues:
   - `getTasksSnapshot` reuses unfiltered `listTasks` (limit 200, due_date asc), so done/missed history fills the cap and counts drift toward 0 as history grows. Filter to todo/doing with a due date, or use count queries.
   - `weekStart` (`reads.ts:144-157`) is a bare date, which compares as UTC midnight, so it disagrees with the zoned dashboard (`app/page.tsx:93-97`) for 7–8h a week. Copy the dashboard's approach.
4. **Batch executors aren't atomic, so partial failure leaves balances stale.**
   - `executeUpdateFinance` (`writes.ts:1506-1688`) exits early via `fail()`, which skips the balance recompute (`:1690-1698`). Ledger rows are committed, but `accounts.balance` is stale and the audit row says `error`.
   - Now (S): recompute touched accounts in `finally`, and record `{applied, failedAt}`.
   - Properly (L, **migration, flag**): a plpgsql `apply_finance_ops(user, ops jsonb)` in one transaction, using the `claim_next_job` revoke pattern (`0035:24-53`).
   - Review `executeUpdateStock` (`:1058`) and `executePeopleUpdate` (`:2830`) the same way.
5. **Windows timeouts don't kill the process tree.** (M, high payoff.)
   - `worker/worker.py:507-517`: `subprocess.run(shell=True, timeout=…)` on Windows kills only cmd.exe, then `communicate()` blocks on the claude grandchild. Heartbeats keep the job fresh, so the follow-up timeout never fires and the queue stalls.
   - `run.mjs:185-191`: `spawnSync` with shell, same problem. The 50-min dispatch clamp isn't enforced, and a run past `LOCK_STALE_MS` (105 min) lets a poll re-claim the same full-power dispatch, so it **runs twice**.
   - Fix: async `spawn` + a timer → `taskkill /PID <pid> /T /F`; in Python, `CREATE_NEW_PROCESS_GROUP` + taskkill. Async spawn also keeps the lock heartbeat alive.
6. **Follow-up jobs report success without creating anything.**
   - `worker.py:528-543` returns `created_task_ids: []` when the result marker is missing, and `app/api/worker/route.ts:223-233,488-491` marks the job `done`.
   - Dead-lettered follow-ups never surface on the task; `failJob` only handles ocr/tts/reel.
   - Fix: verify the created ids exist for that user (or `updated_original`), else `failJob`; on dead-letter, append `## Follow-up failed — <date>` to the task.
7. **Worker child can read an owner-level token.**
   - `worker.py:506` passes the full env, including `WORKER_TOKEN` (which is `MCP_BEARER_TOKEN`, mapping to the owner with confirm rights, revocable only by redeploy; `route.ts:1539-1548`), to a `claude -p` with permission bypass (`:496`) and shell.
   - `run.mjs:159-163` already strips its own token for exactly this reason.
   - Fix: strip it from the child env; give the child its own owner PAT via `mcp.json` only; restrict `--allowedTools`; split the worker token from `MCP_BEARER_TOKEN` (`app/api/worker/route.ts:52-60`).
8. **Proposals never expire.**
   - `loadProposal` (`app/lib/mcp/audit.ts:52-65`) has no age check, and `executing` rows are never reaped.
   - If `finalizeClaimedProposal` (`writes.ts:3163`) throws after the write ran, the client sees failure and a retry double-applies.
   - Fix (no migration): reject proposals older than 24h (`created_at` exists), mark `executing` rows older than 15 min as `error`, and make a finalize failure non-fatal.
9. **No CI; the riskiest paths are untested.**
   - There's no `.github` on main, and Vercel ships main on push.
   - Untested: `confirmAction`, every executor, the route zod schemas, `reads.ts`, the run.mjs phases and the worker. `test/isolation-proof.mjs` is manual against a live DB.
   - Fix:
     - an Actions workflow: lint/test/build + `node --check overnight/*.mjs` + a PowerShell 5.1 parse check (PR #25 was a PS 5.1 parse fix)
     - extract the in-memory PostgREST fake (`__tests__/mcp-dispatch.test.ts:24-60`) into a shared helper
     - inject `tool()`/`runClaude` into the run.mjs phases so tests push triage payloads through the real schemas (that would have caught #1)
10. **Overnight failures are logged, never escalated.**
    - Failure detection in `digest.ps1:41` is a Haiku model reading logs.
    - The night report mislabels decline-write failures as "approach FAILED" (`run.mjs:1029`).
    - In `buildPhase`, the `building` update sits outside the `try` (`:516`), so one MCP hiccup is FATAL and skips Track B.
    - Fix: a machine-readable `logs/<date>.json`, a deterministic scan, a WhatsApp ping on the same error two nights running, and move the update inside the `try`. (This overlaps the "pipeline health" idea, #6 in the ideas doc.)
11. **Timezone (latent).**
    - `user_settings.timezone` defaults to `'UTC'` (`0011:12`; `app/lib/data/settings.ts:14`). Any unrelated settings upsert (`app/actions/settings.ts:30-38`) creates the row as UTC, and `preferences-form.tsx:43-44` then preselects UTC.
    - `run.mjs:139` dates note headings in UTC, so evening dispatches get tomorrow's date, while `digest.ps1:33` uses local time.
    - Fix: what `AGENTS.md:325` already prescribes (persist the device zone once, with a notice), and use local dates in run.mjs.
12. **No service worker.** `public/` holds only the manifest and icons. Quick capture, called the most important UX constraint (`AGENTS.md:9`), fails offline. Fix: cache the app shell, plus an IndexedDB capture queue replayed with idempotency keys (as the watch API already does). This pairs with Web Push in the ideas doc (#4).
13. **OAuth grants can't be revoked per user.** Tokens are stateless, and the 30-day refresh re-issues forever (`app/lib/mcp/oauth.ts:14-15`, token route `:74-79`). Fix (**migration, flag**): a per-user revocation timestamp in `user_settings`, plus a "disconnect apps" button.
14. **MCP payloads are large.**
    - `list_tasks` returns full notes for up to 200 rows; it was 76K characters on 2026-10-20, which forced the WhatsApp step to spill it to disk.
    - Fix: `includeNotes` (excerpt by default) and `limit`/`dueBefore` params, with the cap and ordering stated in the tool description.
15. **Two auth round-trips per navigation.** `utils/supabase/middleware.ts:28` calls `getUser()` on every non-static request, bearer routes included, and there are 110 more call sites. Use `getClaims()` for reads if the project uses asymmetric JWT keys, and exclude bearer routes from the proxy matcher. (Confidence: medium.)
16. **Docs drift, dead code, stale worktrees.**
    - `README.md:531-535` lists 11 of 65 tools, and its DB setup stops at 0003.
    - `AGENTS.md:335` still says audit/confirm arrive "in a later phase" (both shipped).
    - The ~72 KB `AGENTS.md` loads into every agent run; split it into a core plus per-domain docs.
    - `app/lib/agent/registry.ts` (538 lines) is imported only by a test, and the route's claim that it "mirrors" registry.ts is false.
    - `.claude/settings.local.json` is tracked despite `.gitignore`.
    - There are 20 worktrees.
