## 0. Fix first: overnight triage writes rejected every night since 2026-09-19

- **What:** migration 0052 added `tasks.ai_state = 'declined'`, and `app/lib/mcp/validate.ts:325` accepts it. But the zod input schema for MCP `update_task` (`app/api/mcp/[transport]/route.ts`, ~566 on main / 582–583 on task-energy) is still `["planned","building","built","failed"]`. The same gap exists in the `list_code_tasks` filter (route.ts ~217–218) and its type in `app/lib/mcp/reads.ts`.
- **Effect:** `overnight/run.mjs:705-709` sends the triage notes **and** `aiState:"declined"` in one call. The schema check rejects the whole call, so the decline reason is lost too. `ai_state` stays null, and the same tasks are re-triaged every night. 13 rejected writes on 2026-10-19 alone (`overnight/logs/2026-10-19.log`).
- **Why tests missed it:** they exercise the validator, not the registered zod schema.
- **Fix:** branch `ai/fix-ai-state-declined`. A single `AI_STATES` source of truth feeds every schema and filter, plus a regression test that goes through the real MCP schema. Status: see the PR / branch notes.

## 2. `task-energy` adversarial review

Vitest: 82 files, 1,511 tests, all pass. No data-loss or tenant-isolation bugs found. **Merge blockers: #1, #2 and #3. #4 should go in the same pass.**

1. **Pulling a parent's due date earlier silently rewrites its subtasks.** (Medium, high confidence.) `app/actions/tasks.ts:249-260`, `app/lib/mcp/writes.ts:1919-1932`.
   - The confirm summary says "due → X" for one task, but N+1 rows change.
   - Only the parent's Google Calendar event is re-synced (`tasks.ts:372`, `writes.ts:1984`), so a pushed subtask's event goes stale.
   - The subtask writes happen *before* the parent update, so a failed parent update leaves the subtasks already moved.
   - Fix: list the pulled-in steps in the summary, re-sync their events, and update the parent first.
2. **`delete_task` hides the cascade.** (Medium, high.)
   - `writes.ts:2051` says "this cannot be undone" but doesn't mention that the FK cascade deletes every subtask, completed ones included.
   - The web label counts only subtasks in the current view, so a cross-group parent shows a plain "delete".
   - Fix: count the subtasks into the summary.
3. **A subtask's due date can be cleared, which orphans it.** (Medium-low, high.)
   - `tasks.ts:233` / `writes.ts:1899` only guard against tasks that *have* children.
   - Clearing a child's date drops it from the planner and NOW/LATER, while the parent still counts it as open ("2 of 3" forever).
   - MCP `create_task` already requires a subtask due date (`writes.ts:~817`).
   - Fix: reject `dueDate:null` when `parent_task_id` is set.
4. **MCP `complete_task` no longer completes a missed or done task, and the error is misleading.** (Medium-low, high.)
   - `lifecycle.ts:92-99` only updates open tasks and otherwise reports "resolved meanwhile", which reads like a race.
   - Fix: load the status first, then allow missed→done deliberately, or return "already done/missed".
5. **Counts still include hidden subtasks.** (Low-medium.)
   - `app/lib/snapshots/tasks.ts:22-29` feeds MCP `tasks_snapshot` (`reads.ts:162`) and the assistant `get_snapshot` (`tools.ts:901`). Subtasks of a missed parent inflate "overdue", and windows are counted by end date rather than planned day.
   - `stream.ts:874` counts every subtask in the inbox nudge.
6. **The planner pulls steps early at the edge of calendar coverage.** (Low-medium.)
   - Days without calendar data are treated as unusable, so a window straddling the month-grid edge lands on the last covered day and then jumps when the month rolls over.
   - The energy budget plans over 3 days, `get_snapshot` over 7.
   - The existing test (`__tests__/subtask-plan.test.ts:102`) doesn't cover a straddling window.
7. **Snooze/defer can silently do nothing.** (Low-medium.)
   - Web: `stream-client.tsx:832` sets `notBefore = min(dateKey, due_date)`, which is a no-op at window end. The card disappears and then comes back.
   - Watch: `writes.ts:296` returns ok with a new `atWindowEnd` flag that old builds ignore.
   - The watch sorts subtasks by window end, not planned day (`watch/today.ts:216-218`).
8. **Breakdown edge cases.**
   - An overdue parent pays for the Haiku call before validation rejects it (`decompose.ts:185` vs `decompose-ops.ts:69`).
   - Count errors are ignored (`decompose.ts:95-102`).
   - Two simultaneous confirms create two sets of steps.
   - `recordProposal` can throw, and nothing catches it in `proposeBreakdown`.
9. **`create_task` with `parentTaskId` previews the wrong group.** The executor inherits the parent's group (`writes.ts:823`), but the preview names the requested one.
10. **Migration 0053 (flagged; do not auto-apply).**
    - The composite same-user FK is good, RLS from 0001 covers the new columns, and no backfill is needed.
    - Gaps: nothing in the DB blocks self-parenting or nesting deeper than one level. Suggest `check (parent_task_id is distinct from id)`. Also, the cascade wipes completed subtasks' history.
    - **Deploy order:** every task read now selects the new columns, so the migration must be applied *before* this code ships.
11. **Minor.**
    - Completing a parent adds N+1 to "done this week".
    - MCP `create_task` marks energy as the AI's guess, but `update_task` marks it as the user's, so agents can write "user-owned" energy values.

**Missing tests:** subtask pull-in combined with calendar sync and its summary; a window straddling coverage; clearing a subtask's date; `tasksSnapshot` with a missed parent; two breakdowns confirmed at once; the watch's `atWindowEnd`; and the MCP input schema itself (the `declined` gap).
