# Mindboard as a quest log: ideas, 2026-10-20

Status: **PROPOSALS, none approved.** Lucca picks; nothing here is built. Written so a fresh model can pick any item up cold: each idea has the problem (with evidence from live data), the design, an implementation sketch against the current codebase, effort, risks, and how we'd know it worked.

**North star (Lucca, 2026-10-20):** "The whole point of Mindboard is that it becomes almost like a quest indicator that some games have that tell you what you need to do and what you should be doing, and I feel like a lot of my tasks come from whatsapp messages and I always end up forgetting."

Research briefs behind this doc are appended at the end (game quest-log design, message→task extraction, prospective memory and reminders).

## Design rules every idea must respect (from the repo's own docs)

- **"One ranked queue you clear."** (`docs/REDESIGN.md`, Lucca 2026-07-05.) The quest framing sharpens this into one *tracked* objective on top of that queue.
- **"A stale task manager is worse than no task manager."** (`CODEX_HANDOFF.md`.)
- **A pointer, not XP.** The docs rule out scores, streaks and guilt nudges, and `onboarding-landing-plan.md` rules out gamification checklists. The ideas below borrow games' *legibility* mechanics (tracked objective, quest giver, waypoint/go-link, journal), never their reward mechanics. The precision ledger (idea 9) measures *agents*, not Lucca.
- **Capture speed is sacred.** The bottom input stays the fastest path. Nothing here adds required fields at capture; new fields are agent-filled or optional.
- **Propose → confirm for AI writes** (AGENTS.md). Exceptions must be explicit.
- **Unbuilt intent this fulfils.** `app/lib/agent/registry.ts` names a third consumer, "the proactive 'next best step' planner", that was never built. Idea 3 is that planner.

## The ideas

Ranked by expected impact on "tells me what to do *and gets it done*" ÷ effort. ★ = recommended first wave.

### ★1. Quest anatomy: a stable name, a current objective, and agent "intel"

**Problem.** Observations 1–2. Status is crammed into titles, so titles churn daily and the next physical action is never stated.

**Design.** Games separate the quest *name* ("The Office Hours"), the *current objective* ("Book a seat with Ana"), and the *journal* (lore/status). Do the same:
- `title`: stable. The name you recognise.
- `objective` (new, ≤ 80 chars): the next physical action, verb-first. "Book Ana's Tue 12:50 seat on Canvas".
- `intel` (new, text) + `intel_updated_at`: volatile, agent-maintained status. "2 seats left as of 08:05; Thu seat gone".

**Implementation.**
- Migration (flag for Lucca, never auto-apply): `alter table tasks add column objective text, add column intel text, add column intel_updated_at timestamptz;` RLS is inherited from row policies.
- MCP `create_task` / `update_task` (`app/api/mcp/[transport]/route.ts` + `app/lib/mcp/validate.ts` + `writes.ts`): accept `objective` and `intel`. Writing `intel` stamps `intel_updated_at`.
- Tool descriptions must say: "Never put status, counts or dates-as-news in `title`. Put the next action in `objective`, put status in `intel`." This is the real fix, because agents follow tool descriptions.
- UI: the stream card shows title, then the objective in bold, then intel muted with its age ("updated 6h ago"). The watch row adds `objective`; it's additive, so older builds ignore it.
- Agent skills that write tasks need updating: the daily Canvas check (vault/collector), the overnight triage, and the new WhatsApp step.
- One-time cleanup: an agent proposes splits for existing long titles as a single batch of `update_task` proposals that Lucca confirms.

**Effort.** M (one migration, three layers, a skill-prompt sweep).

**Risks.** Agents keep stuffing titles anyway. Mitigate with a validate-layer warning when a title exceeds 90 characters or contains a time-relative word like "TODAY" or "NOW".

**Success.** Median title length under 50 chars. Every open task with a due date in the next 7 days has an objective.

### ★2. Quest givers and "go to quest" links

**Problem.** Tasks don't say who gave them or where they get done. The LING seat needed one tap on a Canvas page, but nothing in the task opened it. WhatsApp-derived tasks currently store provenance as a text marker inside notes.

**Design.**
- Every quest can carry `source_kind` (`whatsapp | email | canvas | brasa | calendar | self | agent`), `source_ref` (chat JID, Gmail thread id, Canvas URL, Drive doc id), `giver_person_id` (FK → people), and `action_url` (the one link where the task gets done).
- `action_url` examples: `https://wa.me/<number>` for "reply to Carla", the Gmail thread URL, the Canvas booking page, a Showpass link.
- A "↗ go" button appears on the stream card, in the task panel, and on the watch. The watch hands off to the phone.

**Implementation.**
- Migration (flagged): add the four columns, plus a unique partial index on `(user_id, source_kind, source_ref) where status in ('todo','doing')`. That turns the WhatsApp pipeline's notes-marker dedup into a database guarantee.
- MCP create/update accept the fields. `list_tasks` gains `sourceKind` / `givenBy` filters.
- WhatsApp step in the collector: switch from notes markers to `source_ref` and keep the marker line for backward compatibility. Map WhatsApp contacts to people roster rows via aliases; there's already an `aliases` array on people.
- The person dossier (`/people/[id]`) gets a "quests from them" section.

**Effort.** M.

**Risks.** Deep links rot (Canvas URLs change per term), so treat `action_url` as best-effort. Privacy: the JID is a phone number; it already lives in Supabase for this user only.

**Success.** At least 70% of agent-created tasks have an `action_url`. "Reply" tasks get closed faster (median time-to-close, before vs after).

### ★3. Tracked quest: one objective on the HUD, and a daily loadout

**Problem.** The stream shows many elevated cards, and the watch shows lists. Nothing says "do *this* now". Games limit tracked quests (often to one) and show its objective line on the HUD at all times.

**Design.**
- **Tracked quest.** Exactly one at a time. Either Lucca pins it ("track") or a picker chooses it.
- The picker scores urgency (existing `urgencyScore`) × fit-now. Fit-now means: the free gap until the next calendar event ≥ `estimated_minutes`; energy cost ≤ remaining energy budget (`todayEnergyBudget`, task-energy); inside the task's `not_before` window; source not `hud=false` (idea 6).
- It shows the objective (idea 1), a reason ("closes today 12:50", "fits your 40-min gap"), and the go link (idea 2).
- **Daily loadout.** The morning brief proposes 1 main + 2 side quests, each pre-placed in a free gap as a time-block. That's an implementation intention: *when/where* plus *what*. One tap (or a "ok" reply, see idea 5) accepts.
- Only loadout quests and the tracked one are on the HUD. Everything else is one swipe away.

**Implementation.**
- Pure `pickTrackedQuest(tasks, schedule, energyBudget, now, timeZone)` in a new `app/lib/snapshots/quest.ts`, table-tested like `urgency.ts`. Reuse `freeGaps` from `scheduleSnapshot` and the task-energy budget.
- State: `user_settings.tracked_task_id uuid null` + `tracked_pinned boolean`. Auto picks aren't stored; they're recomputed per read.
- Surfaces:
  - top of the stream (`app/page.tsx` stream section)
  - watch API: an additive `tracked` field in `WatchToday`
  - MCP `get_snapshot` returns `trackedQuest`
  - a new MCP `track_task` tool (propose → confirm)
  - the brief's first line
- Loadout: an MCP read `propose_loadout(date)` returns 3 candidates with suggested blocks. Acceptance uses `update_task` (dueTime/durationMin, optional pushToCalendar).

**Effort.** M. The picker is S; the surfaces add up.

**Risks.** A bad auto-pick erodes trust. Show the reason, and allow "not now" (snoozes the pick 2h). Over-scheduling: limit the loadout to 3 and never auto-push to the calendar without acceptance.

**Success.** Loadout acceptance ≥ 50% of days. Tracked-quest completion ≥ 1/day on weekdays. Fewer "renamed but not done" chains (observation 1).

### ★4. Closing-window escalation (timed quests)

**Problem.** Observation 1 exactly. Opportunities with an expiry (office-hour seats, ORCA exam windows, a grant due a month before an event, form deadlines) only ever reach Lucca as a quieter or louder task title.

**Design.** A quest can carry `expires_at`, meaning the moment the chance is gone (different from the due date). An escalation ladder runs as the window closes:
- T-72h: the brief.
- T-24h: it becomes the tracked quest.
- T-6h: one WhatsApp ping to his own chat, at the next free gap.
- T-1h: a final ping.

**Budgets.** At most 2 pings per day across all quests, quiet hours 22:00–08:00, and "snooze"/"drop" by reply (idea 5).

**Implementation.**
- Migration (flagged): `tasks.expires_at timestamptz`, plus an `escalations` table (task_id, rung, sent_at) for idempotency.
- Sender: a new track in the home PC's 5-minute poll (`overnight/run.mjs` already polls). It reads tasks with `expires_at` in a rung window, checks budgets, and POSTs to the WhatsApp bridge `/api/send` with recipient = Lucca's own chat only. Hard-code the recipient; don't parametrise it.
- Second channel, recommended to add later: **Web Push**. Mindboard has no service worker or push code at all (`app/`, `public/`), so today the indicator only exists while the app is open. iOS 16.4+ delivers Web Push to installed home-screen PWAs. Add `public/sw.js`, a `push_subscriptions` table (flagged), and a VAPID key in Vercel env. Escalations then pick the push channel first and fall back to WhatsApp. This also helps every other "reach out" idea.
- Pair this with **availability windows for top-level tasks.** Today `not_before` only applies to subtasks, and the due date doubles as the start date (gap noted in the feature map). Allowing `not_before` on any task lets "ORCA window opens Oct 19" or "LING quiz opens 7am" be data instead of title text, which the picker (idea 3) and the escalation can read.
- Agents set `expires_at` when they learn of a window. The Canvas check knows seat times; the WhatsApp step knows "até sexta".

**Effort.** M.

**Risks.** Nagging. The budgets and quiet hours are mandatory, not tunable defaults. Bridge down: fall back to the brief only, and log a heartbeat failure (idea 7).

**Success.** Zero "window closed while the task sat open" events per month, measured by `expires_at < completed_at`, or still open at expiry.

### ★5. Workshop split: keep the dev backlog off the quest log

**Problem.** Observation 3. Mindboard's own dev tasks are 45% of the open list and pollute urgency, the stream and the brief.

**Design.** Groups gain `hud boolean default true`. Set it false for "Mindboard" (and any project group used as an agent queue). The stream, watch, tracked-quest picker, loadout and brief ignore `hud=false` groups by default; there's a "workshop" filter to see them. Overnight agents still read them.

**Implementation.**
- Migration (flagged): `groups.hud`.
- Filter in `stream.ts`, `watch/today.ts`, `tasksSnapshot` (add a separate `workshop` count) and the picker.
- MCP `manage_group` accepts `hud`.

**Effort.** S.

**Alternative.** Move dev tasks to GitHub issues (`gh issue create`) and make the overnight agent read issues. Bigger change, cleaner separation. Not recommended now.

**Success.** HUD and brief counts reflect life tasks only.

### ★6. Pipeline health is a quest ("your party is hurt")

**Problem.** Observation 5. Silent failures persisted 2–4 weeks: triage writes since 09-19, reels since 09-26. Collector steps degrade quietly.

**Design.** Every scheduled job writes a heartbeat: collector, overnight orchestrator, run.mjs poll, worker.py, reel worker, Canvas check, WhatsApp bridge, and the WhatsApp step. Each heartbeat records name, last_ok_at, last_error, expected_interval. When a job misses two intervals or errors twice, Mindboard auto-creates one high-priority quest per failure: "Fix: overnight triage writes rejected (since Sep 19) — enum mismatch". The quest closes itself when the heartbeat goes green. There's also a small health strip in the stream and the brief.

**Implementation.**
- Migration (flagged): a `pipeline_heartbeats` table, user-scoped with RLS.
- Writes: an MCP tool `report_heartbeat` (direct write, no confirm, since it's operational telemetry; document the exception) or a bearer-auth route like the watch API.
- Checker: a cron (Vercel cron or run.mjs) creates or closes the fix quest.
- It feeds the precision ledger (idea 9).

**Effort.** S–M.

**Immediate one-liner while this is unbuilt:** add `declined` to the MCP aiState enum (see the review findings).

**Success.** No failure lives longer than 2 intervals unnoticed.

### 7. WhatsApp self-chat as the quest console

**Problem.** Capture and triage happen where Lucca isn't: the PWA. Where he is, all day, is WhatsApp. Check-ins died (observation 4) partly from friction.

**Design.** His own chat becomes a two-way console.
- **Out:** the morning quest card (tracked quest, loadout, replies owed), plus escalation pings (idea 4).
- **In:** short replies, a deterministic grammar first with an LLM fallback:
  - `done 2` / `done carla`
  - `snooze 1 2h`
  - `drop 3`
  - `+ buy velcro fri` (capture)
  - `ok` (accept the loadout)
  - `e3 s7` (check-in: energy 3, sleep 7h)
  - `track lingo`
- Every command gets a one-line confirmation in the same chat. Destructive commands need `yes`.

**Feasibility check (2026-10-20).** The bridge does **not** reliably capture the self-chat. `messages.db` has only 15 rows under `17789038375@s.whatsapp.net` (the last on 2026-08-10, all with empty content) and none under his LID chat. An agent message sent to that JID via `/api/send` on 2026-10-19 isn't stored at all. Two options:
- **(a) Recommended:** a dedicated one-member group ("Mindboard 🎯", Lucca alone). Group messages are captured reliably (the BRASA groups prove it), `is_from_me=1` rows land under a stable `@g.us` JID, and `/api/send` can target that JID.
- **(b)** Patch the Go bridge's message handler to persist self-chat and outgoing-API messages, which means modifying whatsmeow event handling in `whatsapp-bridge/main.go`.

**Implementation.**
- A local poller on the home PC (Task Scheduler every 2–5 min, or a whatsmeow event hook in the bridge). It reads only messages in the console group's JID with `is_from_me=1` since the last cursor.
- It applies commands through Mindboard's MCP with his personal `mbp_` token, or the watch-style bearer API, and replies via the bridge `/api/send` to the self-chat only.
- Numbered items refer to the last card sent; store the card's id→task map locally.

**Effort.** M–L.

**Risks.** Parsing mistakes (always echo what was done; `undo` reverts the last write via the audit log). Bridge session expiry (~20 days; heartbeat, idea 6). Never read or act on other chats in this path.

**Success.** Daily check-in rate > 70%. Capture via WhatsApp exceeds capture via the PWA input.

### 8. Fresh-start camp (weekly reset)

**Problem.** Lists rot. Undated and stale items make the list feel unwinnable, and an overdue pile demotivates.

**Design.** Monday morning (fresh-start timing), "Camp" walks through every overdue, stale (untouched 14 days) or undated high-priority quest, one card at a time. Four buttons:
- **Re-date:** suggest a free slot.
- **Shrink:** decompose into a next action; uses `decompose_task` from task-energy.
- **Hand off:** `✦ do it`.
- **Drop:** mark missed, no guilt.

It ends by choosing the week's main quest. It's also available via self-chat.

**Related fix: cap lateness in urgency.** `urgencyScore` adds `daysLate × 10` without bound (`app/lib/snapshots/urgency.ts:53-54`). A task 5 days late outranks everything due today, so stale items permanently own NOW (the 2026-10-19 morning digest showed 12 overdue and 0 done). Cap the lateness term (for example at +20), and route anything past the cap to Camp instead of the top of NOW.

**Implementation.**
- `tasks.last_touched_at`: touch on any user edit; agent `intel` writes don't count.
- New route `/camp`, mobile-first sheet stack.
- MCP `camp_snapshot` read.
- Brief section on Mondays.

**Effort.** M.

**Success.** Open undated high-priority count trends down. The weekly camp is completed ≥ 3 of 4 weeks.

### 9. Precision ledger for AI-created quests

**Problem.** Agents now create tasks from Canvas, email and WhatsApp. If precision drops, Lucca stops trusting the list, and nothing measures it.

**Design.** Per `source_kind` (idea 2), track the outcomes of agent-created tasks: done, missed, deleted untouched, edited title, closed by auto-close, still open after 14 days. Report weekly precision and median time-to-done in the health strip and the brief. Feed it back: when a pipeline's 2-week precision is under 60%, its daily cap halves automatically, and its prompt gets the recent false positives as negative examples.

**Implementation.**
- Mostly a read: SQL over tasks + `ai_audit_log` (source = mcp, tool = create_task).
- Store per-pipeline caps in `user_settings` or a small `pipeline_settings` table.

**Effort.** S, once idea 2 lands.

### 10. Person-cued quests (right person, right moment)

**Problem.** Event-based cues ("when I see Davi, ask about the book") are remembered far better than time-based ones. Mindboard has the people, the calendar and now the chats, but never connects them.

**Design.** Before a calendar event with a person, or when a chat with them is active, surface open quests whose giver is that person. Examples:
- Before Tuesday's English class: "Davi: confirm whether you have *Timezones 4*" (a promise to Build Up).
- Before the BRASA Monday meeting: "Davi: COLSA logo".

This shows in the brief ("before your 4pm with X: 2 open quests") and as an optional ping 15 minutes before (counts toward the idea-4 budget).

**Implementation.**
- Map people ↔ calendar attendees and title keywords (aliases already exist), and people ↔ WhatsApp JIDs (`people.whatsapp_jid`, new nullable column, flagged).
- Read `quests_for_person(personId)`.

**Effort.** M (depends on idea 2).

### 11. Promise ledger

**Problem.** The most reputation-costly forgotten tasks are promises Lucca made ("vou confirmar com o Davi"). The WhatsApp step's `do` bucket catches some, but they're stored as ordinary tasks.

**Design.** A `kind = promise` on quests, with promisee = giver and an age counter. The brief shows "Promises outstanding: 2 (oldest 4 days, Build Up)". When Lucca next messages the promisee, an LLM check ("does this message fulfil the promise?") proposes auto-completion.

**Implementation.** A `kind` text column with default 'task' (flagged), plus WhatsApp-step prompt changes and the fulfilment check in the same step.

**Effort.** S on top of idea 2.

### 12. Check-in revival

**Problem.** Observation 4.

**Design.**

### ★14. Plan chips: a one-tap "when/where" on every captured quest

Added after the prospective-memory research. Of everything in that brief, this is the most evidence-backed mechanic.

**Problem.** A task read in WhatsApp arrives with a *who* but no *when* or *where*. Recall then falls back on time-based prospective memory, the weakest mode. Lab: event-based beats time-based (Einstein et al. 1995). In-situ: place-cued intentions were forgotten less than time-cued ones (Sellen et al.).

**Design.** Every agent-captured quest gets 3–4 agent-drafted cue chips plus "drop":
- **person:** "next time I see Carla"
- **place:** "at the Nest"
- **routine:** "after dinner"
- **clock slot:** "Tue 10:00", from the free gaps

Lucca picks one tap (or replies with a number in the WhatsApp console, idea 7). There's an optional five-second "picture it" line. Unplanned items wait in an **Unplanned** tray that doesn't count as overdue and doesn't crowd NOW until a cue is picked.

**Evidence.**
- Implementation intentions: d = .65 on goal attainment across 94 tests (Gollwitzer & Sheeran 2006); d ≈ .45 for prospective memory specifically (Chen et al. 2015).
- Field reality is a few points: date+time prompts added +4.2 points of flu-shot uptake, and date-only prompts did nothing (Milkman et al. 2011). So the chip must carry a concrete slot or a cue, not just a date.

**Implementation.**
- `tasks.cue_kind` (`person | place | routine | time | none`) + `tasks.cue_ref` (person id, place text, routine id, or ISO slot). Migration flagged.
- Time cues reuse time-blocks (`dueTime`/`durationMin`).
- Person cues feed idea 10 (surface before an event with that person). Routine cues hook into `recurring_tasks` completions ("after Dinner is ticked").
- The agent drafts the chips at creation, in the WhatsApp step and in `create_task` callers. A new optional `cueSuggestions` field rides on the task proposal.
- UI: a chip row on the stream card and in the task panel.

**Effort.** M.

**Risks.** Reflex taps on unrealistic slots. Show the chosen cue back at the cue moment, with Done / Re-cue / Drop and no blind snooze ("closed-loop reminders").

**Success.** At least 60% of agent-captured quests get a cue within 24h, and cued quests finish faster than uncued ones.

### 15. Tiers: Main / Side / ≤2 dailies, and only Main can be overdue

Added after the game-design research.

**Problem.** Everything is equally "a task", so a missed self-set nicety looks as alarming as a missed exam.

**Design.**
- **Main** = has an external deadline within 7 days (exam, client ask, club shift).
- **Side** = everything else.
- **Dailies** = at most 2 recurring items surfaced per day.
- Only Main quests can show as overdue. Side quests past their date quietly drift to Camp (idea 8).
- **Precedent:** Skyrim's quest groups (Main/Faction/Side/Misc) and a separate misc journal (UESP). Destiny 2's bounty saga: removing bounties was "an over-correction", and later seasonal challenges were designed to cut "bounty fatigue and FOMO" and "reduce the penalties for missing a week".

**Implementation.**
- Derived, not stored: `tier = main` if (due within 7d **and** (source is external, i.e. `source_kind` ≠ self **or** group type is `course`/`work`)) **or** a manual pin. That's a view-layer change on `stream.ts`/`watch/today.ts` once idea 2 exists.
- The `tasksSnapshot` overdue count counts Main only and reports Side separately.

**Effort.** S–M.

**Risk.** Everything gets labelled Main. Keep it derived, with the manual pin capped at 3.

### 16. Guidance dial: Guided / Open / Off

Added after the game-design research.

**Design.** A setting, borrowed from Assassin's Creed Odyssey's Guided vs Exploration modes, and Baldur's Gate 3 softening precise markers into area markers.
- **Guided:** one tracked Now card plus the loadout.
- **Open:** three cards.
- **Off:** today's plain list.

A deadline safety net (Main quests inside 24h) stays on in every mode, because Elden Ring shows the cost of no guidance (players missing NPC steps, "buy a notebook"). The watch is always Guided.

**Why.** Autonomy is one of the three needs that predict games' motivational pull (Ryan et al. 2006). Lucca can turn the pointer down on days he wants to just look at the list.

**Implementation.** A `user_settings.guidance` enum (flagged migration) read by the stream.

**Effort.** S, after idea 3.

### 17. Weekly chronicle, not XP

Added after the game-design research.

**Design.**
- A Sunday-evening card (brief + app + optional WhatsApp) written by the overnight agent: what got done this week, grouped by questline (course, BRASA, English classes, home), including things finished outside Mindboard that agents saw (a reply sent, a booking made).
- No points, no streak counter.
- The watch shows "4 this week". Show a rolling window ("last 4 weeks best") rather than a counter that resets.

**Evidence.**
- Informational positive feedback enhances intrinsic motivation (d = +0.33), while expected tangible rewards undermine it (d = −0.28 to −0.40), across 128 experiments (Deci, Koestner & Ryan 1999).
- Highlighting broken streaks demotivates (Silverman & Barasch 2023), and Duolingo itself concedes a broken streak can "feel quite demotivating".
- Lally (2010): missing one day doesn't materially affect habit formation.

**Implementation.** A read over completed tasks + `ai_audit_log`, rendered by `overnight/digest.ps1` (it already writes Monday digests) into the vault and the app.

**Effort.** S.

**Risk.** Inflated trivia. Count Main quests and finished chains, not every routine tick.

### Notes from the game research that sharpen ideas 3, 8 and 4
- **Order matters (idea 3 after idea 8).** A Now line switched on over an un-triaged pile surfaces stale items and loses trust. Ship Camp (or at least the lateness cap) before the tracked quest. Lucca's own 2am cleanup on 2026-10-20 means the pile is small right now, which is the cheapest moment to start.
- **Quest chains with an honest head start (idea 3 + task-energy subtasks).** Pre-stamped loyalty cards were completed 34% vs 19% (Nunes & Drèze 2006, the endowed-progress effect). Show "Essay 2/5" under the Now card, credit only real completed work, and cap chains at 5 steps. Habitica users relabelled tasks to game the system (Diefenbach & Müssig 2019).
- **Timed quests (idea 4).** Show a countdown chip only inside 72h. After the deadline the outcome is "missed: ask for an extension / drop", never a penalty. Todoist Karma's overdue penalty is the counterexample.
- **Quest givers (idea 2).** Show "From Carla · WhatsApp · Oct 19" with the message on tap. Never show "waiting X days", which reads as guilt.

## Cross-cutting rules from the research (apply to every surface)

- **Notification budget: about 3 pushes a day** (morning brief, pre-event cues, evening close), with hard deadlines allowed to override. Batching to 3 a day beat the status quo, and *zero* notifications raised anxiety (Fitz et al. 2019, N=237). A single notification costs attention almost as much as using the phone (Stothart et al. 2015).
- **Every reminder closes a loop.** Its options are Done / Re-cue / Drop. A bare "snooze" isn't one of them.
- **Expect decay.** Tailored nudges lost their effect within about 28 days (HeartSteps, Klasnja et al. 2019). Vary wording and surfaces, and log "acted within 30 min" per mechanic so dead mechanics get cut.
- **No guilt framing.** Self-forgiveness after procrastinating predicted less later procrastination (Wohl et al. 2010), and the top gym-megastudy arm rewarded *returning* after a miss (Milkman et al. 2021). Camp (idea 8) should feel like "welcome back", not a red overdue wall. This matches the repo's own ban on guilt nudges.
- **The evidence is thin in places.** There's no controlled test of next-action titles, person-cued reminders or visible timers, and no study of overdue to-do lists. Treat those ideas as experiments with the metrics above.
